# blackbox-mod 37.3.3

Thomas's fork ([Maigre/blackbox-mod](https://github.com/Maigre/blackbox-mod)) of JOEBOX 1, the unofficial feature
mod for the **original 1010music Blackbox** (Mk1) on stock firmware **3.1.9**. Everything 37.3.2 has is still there
(37.3.1's Clip Window features on JOEBOX 1 rc4: Slip, Region, Loop Len, Fit and Loop Fade on Clip pads, the knobs on
a Clip pad's waveform, the Slip knob and the rest of JOEBOX 1). This release removes the click, or the short doubled
sound, that a Clip pad could make once a pass where its loop comes round. TOOLS shows `37.3.3`.

**Status: a test release.** Every part passes the emulated suites (`./check.sh`: 31 suites, 0 failed). None of it has run on a
unit yet; it answers Gate 3b's finding F-a, traced on a unit running 37.3.2d.

## New since 37.3.2

- **No click where the loop comes round.** A Clip pad whose Attack is 0 (stock's default for a pad) started each
  pass of its loop without stock's short fade-in. That is fine where the file itself starts, after a short gap. But
  with Slip, a Region that starts after the file's beginning, or Loop Len, the pass starts in the middle of the audio;
  and with a Region or Fit the loop has no gap, so the end of the last pass is still fading out when the new one
  starts. Before, you heard a click once a pass, or the audio twice over for about 5 ms (one bench take: a step of
  0.09 where the take's own are about 0.003). Now that start fades in over 256 samples (5 ms), like every other step of the loop: the pass is the same
  crossfade as any other Sync step, and its timing does not move by a sample.
- **A slipped launch fades in too.** A pad started on a slipped position (or a Region past frame 0) fades in over the
  same 5 ms instead of starting at full level in the middle of a sound. A pad started at the file's own beginning
  still starts at full level, as stock does.
- Nothing changes on a pad with an Attack set (stock already fades it in), on a pad that uses none of Slip, Region,
  Loop Len and Fit, or on a Slicer pad.

The second file, `BBEXTRA.BIN`, changes with this release (the fix runs from the chip's second flash bank).

## Install

1. You need **two files from the same build**: `BLACKBOX.bin` and `BBEXTRA.BIN`. Patched firmware images are not
   distributed. Make them from your own copy of 1010music's stock 3.1.9 `BLACKBOX.bin` (from
   <https://1010music.com/downloads>), either with the release's patch file, `python3 apply.py BLACKBOX.bin
   blackbox-mod-37.3.3.json` (it checks the stock file and the result by SHA-256 and writes both files), or from
   source: `RELEASE=1 ./build.sh && python3 patch.py solo slice duck chord cond filter cpu od comp seqfix fx2 munchi
   master fault cave` gives `out/<sets>/BLACKBOX.bin` and `out/BBEXTRA.BIN`.
2. Keep the stock `BLACKBOX.bin` somewhere safe: it is your way back.
3. Copy **both** files to the root of the microSD card, over the old ones if they are there.
4. With the Blackbox on its normal power supply, hold BACK + INFO while powering on, and let go when the install
   screen shows.
5. The first boot **restarts itself once**, a second or two in: that is the second file being written to the chip's
   second flash bank. It does so on every unit, 37.3.2 and 37.3.1 included, since their second file is not this one.
   Leave the card in and the power on until it is back up.
6. TOOLS shows **`37.3.3`**, with **no `!`** in front of the load figures.

A `!` means the second file is missing or from another build: Prism, Confetti, the insert effects, Slip, Region,
Loop Len, Fit and Loop Fade are then off, the waveform knobs are stock's grey and the playhead line is stock's
(everything else works). Put the `BBEXTRA.BIN` that belongs with your `BLACKBOX.bin` on the card and power off and on.

## Back to stock

Put 1010music's stock 3.1.9 `BLACKBOX.bin` on the card and install it the same way (BACK + INFO at power-on). The
second flash bank keeps this build's code, unused: stock firmware never looks at it, and it does not touch the unit's
calibration.

## Known issues

- **Not yet run on a unit**: the fix is measured under emulation only (see Status).
- The fade-in softens the first 5 ms of a slipped pass or launch. On a loop cut right on a hit, that hit's attack is
  slightly softer at the loop point than elsewhere (stock does the same at every other step of the loop).
- Where a whole file's end and start do not meet, Slip's fold inside a step is still a hard splice (Loop Fade cannot
  reach a whole file). The click F-a reported was not that.
- 37.3.2's known issues all still apply: `notes/releases/37.3.2.md`.

## Images (built locally; not in git)

Built 2026-10-17 with Arm GNU 14.2 from the commit that sets `src/release.h` to 37.3.3, on branch `rc4-sync`, full set
`solo slice duck chord cond filter cpu od comp seqfix fx2 munchi master fault cave`, with `BANK2_NEW=1` (bank 2's
code changed since 37.3.2). Bank-2 payload: id `0x7f4ed13e`, length `0x4220`, sum `0xfbc60061`, byte for byte the same in
both builds; each `BLACKBOX.bin` carries that id and sum and lets the card loader write bank 2. Bank 1 (`.cave`):
57 080 of 57 736 B in the release build, 57 720 in the dev build; `.bank2` 16 896 B.

The dev build (`37.3.3d`) also carries the bench's tools: its USB peek reads only the unit's memories and a few screen
registers, its poke writes only RAM, and a parameter mailbox lets the bench set a pad's rows as its knobs do. None of
that is in the release build, whose image is the same without them.

`apply.py` with `blackbox-mod-37.3.3.json` reproduces the release pair; a release build from this source with the
same toolchain gives the same bytes. Never put a dev build on a unit you lend or sell: its USB poke writes RAM, which
is enough to crash it.
