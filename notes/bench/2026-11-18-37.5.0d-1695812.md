## The control: 37.5.0d `7f3e757` (note repeat in bank 1, no split)

Put back at 13:58 the same way (the 1695812 pair kept in `from-card-20261118-135833`), BACK + INFO by Thomas: boot
#2, no fault, bank 2 `94675216 0001b0e0 e2e1f8a5` (its own length and sum), the call site `0x080A0A44` a direct
`bl` into bank 1's `repeat_pad_down`. The same two holds by hand: `hold` 1 for 4.0 s and 4.4 s, `held` `0x0000`
throughout. **So the split did not do this**: on 37.5.0 as it shipped on 12/11, a held pad never reaches the
note-on site `0x080A0A44` (or reaches `repeat_pad_down` with a pad id or launch mode that makes it pass the note to
stock). Note repeat is JOEBOX 2's (`37ea8f7`, 23/10), merged 12/11, and had not been played on this unit before
today. Upstream's README describes the gesture used here. Open as its own row.

## Seen on the way

- **The bank-2 id does not tell 1695812 from 7f3e757**: both read `0x94675216`. `build.sh` hashes `BANK2_SRCS`,
  `munchi_dsp.cpp`, `b2head.c` and the kit, not the modules `b2split.py` moves, so the card's « id `0x94675216` »
  could not have caught a wrong payload; the length and the sum did (the loader rewrote bank 2 at each install, as
  the sum differs). Cheap fix: put the split's modules in the hash.

  Not replaced (a card write is Thomas's say).
